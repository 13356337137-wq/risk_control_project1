# 一、现状：四层，与你的三侧是这样对应的

| 契约四层 | 对应你的说法 | 查什么 | 结论上限 |
| --- | --- | --- | --- |

# 二、来源侧（你提的第一条，价值最高、成本最低）

银行导出的流水，本身就带可核验的来源凭证：

| 银行 | 文件里现成的凭证（实测） | 能不能核验 |
| --- | --- | --- |
| 招商银行 | 「验证码 79EKKP7E」+ 申请时间 + 官网「交易流水验真」入口 | **能**：官网输入基本项与明细项即可验 |
| 工商银行 | 「申请单号 261014…183」+ 二维码「请扫描二维码识别明细真伪」 | **能**：走行内/二维码渠道验 |
| 建行/农行等 | 流水编号 / 回单编号 | 需各自渠道 |

业务设计建议：

| 项 | 做法 |
| --- | --- |
| 是否必填 | **选填**，但选填字段缺失时写入 limitations（截图件建议必填） |
| 填什么 | 来源凭证号（工号/申请单号/验证码）+ 导出渠道 |
| 谁来核 | 行内系统或官方验真入口（外部层 E1），不做自动爬取 |
| 能证明什么 | 这份文件确由该行生成、且是该时点导出 |
| 不能证明什么 | **不能证明没被改过**；也不能证明账户属于提交人（需身份核验） |

一句话：来源侧解决「是不是这家银行出的」，不解决「有没有被改」。

# 三、文件侧：要拆成「容器」和「像素」两半

## 3.1 PDF 容器取证（纯文件层，能查）

| 项 | 能看出什么 |
| --- | --- |
| 生产者 / 创建与修改时间 | 是不是银行系统生成（例：招行样本 producer=openhtmltopdf.com） |
| **增量更新（多次保存）** | 文件被改过的最强线索：PDF 允许追加修改而不重写 |
| 交叉引用/对象结构异常 | 被工具拼接、删页的痕迹 |
| 字体嵌入与子集 | 后加文字常出现字体不一致 |
| 页树、注释、隐藏层、嵌入附件 | 藏内容或藏页 |
| 加密与权限位 | 是否禁止复制/打印，权限是否被重置 |
| 数字签名与时间戳 | **签名后改动会被发现**（最硬的证据） |

## 3.2 图片 / 图片型 PDF：文件层能查一部分，剩下的必须像素取证

| 能（文件/元数据层） | 不能（必须像素级） |
| --- | --- |
| EXIF：设备、软件、拍摄时间 | 图像内容有没有被 P 过 |
| JPEG 量化表、**二次压缩痕迹** | 局部修补、克隆图章 |
| 分辨率、DPI、颜色空间、ICC | 拼接边界、光照不一致 |
| 缩略图与主图是否一致 | 重采样、透视校正 |
| PNG 块异常、时间戳矛盾 | 屏幕翻拍（摩尔纹） |

**结论（直接回答你的问题）**：

> 图片或图片型 PDF，**文件层只能判断「容器有没有被处理过」，判断不了「图像内容有没有被改」**。
> 内容真伪必须做像素取证（ELA 误差分析、噪声一致性、拼接边界、重采样、摩尔纹、光照、边缘），
> 而且只能给「可疑 / 未发现可疑」，**永远不能给「真」**。

图片型 PDF 还有一个优势要利用：优先取**原始图像流**而不是渲染图，避免二次压缩掩盖痕迹。

# 五、各层能证明什么（防误用）

| 层 | 能证明 | 不能证明 |
| --- | --- | --- |
| 来源侧 | 文件由该行在该时点生成（核验通过时） | 没被改过；属于提交人 |
| 文件侧-容器 | 容器是否被改、签名是否完整 | 内容真实 |
| 文件侧-像素 | 有无编辑痕迹（可疑/未发现可疑） | 「真」 |
| 数据侧 | 内部自洽 | 排除精心伪造 |
| 外部侧 | 与行内/他行数据一致 | 覆盖全部情形 |
