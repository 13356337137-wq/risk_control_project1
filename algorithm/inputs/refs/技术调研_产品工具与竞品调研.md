# 资金流水分析平台工具调研分析（含竞品分析）

:::info
**调研范围**：面向信贷场景的银行流水解析、核验与分析类产品，以及支撑其实现的技术工具链。
**调研方法**：厂商官网与产品页、第三方选型评测、技术论文与开源项目文档的交叉比对。
**适用对象**：产品设计、方案设计、技术选型。
**文档用途**：作为《产品设计文档》的竞品依据与技术选型输入。

## 1 市场格局

### 1.1 四类参与者

| 类别 | 代表 | 核心能力 | 与流水的结合方式 |
| --- | --- | --- | --- |
| 文档智能厂商 | 达观数据、合合信息、易道博识 | OCR、版面分析、文档抽取 | 把流水识别为结构化数据 |
| 风控决策厂商 | 邦盛科技、同盾科技、冰鉴科技 | 决策引擎、关联网络、模型 | 把流水作为特征来源之一 |
| 垂直流水工具 | 银析通、MoneyThumb、Kaaj | 流水分析专用流程 | 端到端处理流水 |
| 综合云厂商 | 腾讯云、阿里云、百度智能云、华为云 | 通用文档解析与 OCR 接口 | 提供底层解析能力 |

### 1.2 按目标客户划分

| 客户类型 | 典型产品 | 交付形态 |
| --- | --- | --- |
| 个人（C 端自助） | 银析通 | 网页与小程序，按次或会员 |
| 金融机构（B 端） | 达观、邦盛、同盾、冰鉴 | 私有化部署或 SaaS，按项目或年费 |
| 开发者（API） | 云厂商 OCR、合合 TextIn | 按调用量计费 |
| 非银放贷机构 | Kaaj、MoneyThumb、Ocrolus | SaaS，按件或按月 |

### 1.3 能力层次

流水处理的能力可分为五层，越往上越贴近决策：

| 层次 | 能力 | 典型提供方 |
| --- | --- | --- |
| L1 | 文件读取与格式判断 | 全部厂商 |
| L2 | 版式识别与字段抽取 | 文档智能厂商、云厂商 |
| L3 | 处理一致性与完整性校验 | 垂直工具、部分文档厂商 |
| L4 | 风险指标与异常识别 | 风控厂商、垂直工具 |
| L5 | 报告生成与决策建议 | 风控厂商、垂直工具 |

不同厂商覆盖的层次不同。文档智能厂商多停在 L2，风控厂商从 L4 切入，垂直工具覆盖 L1 至 L5。

### 1.4 格局特征

+ **L2 已高度商品化**。通用 OCR 与表格识别被云厂商做到按量计费、价格透明，单独做解析工具已无空间。
+ **L3 是分水岭**。能否做一致性校验，决定了产品是「转换器」还是「核验工具」。
+ **L5 存在定位分歧**。国内面向银行的产品普遍止于「提供分析报告」，不输出放款建议。
+ **C 端与 B 端的产品形态差异大**，同一套技术难以同时满足。

### 3.4 数据获取方式的根本差异

海外市场存在两条路线，国内目前只有一条：

| 路线 | 数据来源 | 优点 | 局限 |
| --- | --- | --- | --- |
| 文件路线 | 用户上传 PDF | 不依赖机构开放，适用面广 | 需处理版式、真伪、完整性 |
| API 路线 | 开放银行直连 | 数据可信、完整、实时 | 依赖银行开放接口与用户授权 |

开放银行模式下，流水真实性由银行背书，核验需求大幅降低。国内缺少同等基础设施，文件路线在可预见期内仍是唯一选择。这一差异决定了国内产品的技术投入重点。

## 4 技术工具链

### 4.1 PDF 文本与坐标抽取

银行流水的解析基础是「按坐标重建行列」，因此工具的核心指标是能否提供字符级坐标。

| 工具 | 类型 | 强项 | 局限 |
| --- | --- | --- | --- |
| pypdf | 纯 Python 库 | 元数据、页面对象、加密判断、结构信息 | 文本布局能力弱 |
| pdfminer.six | 纯 Python 库 | 字符级坐标与字体信息完整 | 速度慢，大文件耗时明显 |
| pdfplumber | 基于 pdfminer | 字符坐标、裁剪区域、简单表格 | 继承 pdfminer 的速度问题 |
| PyMuPDF | C 绑定 | 速度快，文本块与坐标，可渲染成图 | 坐标单位为点，需换算 |
| Camelot | 表格专用 | lattice（有框）与 stream（无框）两种模式 | 对复杂合并单元格支持有限 |
| Tabula | 表格专用 | 上手快 | 依赖 Java，能力有限 |

**结论**：合规性判断用 pypdf；文本与坐标抽取用 pdfplumber；渲染比对用 PyMuPDF；表格抽取以自建逻辑为主，Camelot 作交叉验证。

### 4.2 表格结构识别

银行流水属于**规则表格**：列固定、每页重复表头、含合计行。这类表格的难点不在识别，而在：

| 难点 | 说明 |
| --- | --- |
| 跨页表格 | 一条记录被分页切断 |
| 每页表头重复 | 表头行可能被误判为交易行 |
| 无边框 | 列边界依赖空白间距推断 |
| 合并单元格 | 日期或摘要跨多行合并 |
| 文字存储乱序 | PDF 内部对象顺序与视觉顺序不一致 |

针对规则表格，自建「按坐标聚类成行、按列边界切分」的逻辑通常优于通用表格模型，且可解释、可调试。

通用表格模型（如 PP-Structure 一类）适用于版式未知的场景，可作为无模板时的兜底。

### 4.3 学术对比的可用结论

有研究在 DocLayNet 数据集上对多款 PDF 解析工具做了对比，分别评估文本抽取与表格抽取（arXiv:2410.09871）。从该研究的评估框架可得出两点可直接使用的判断：

+ **文本抽取与表格抽取的最优工具不同**，不存在一个工具同时最优。
+ **表格抽取的稳定性明显低于文本抽取**，跨工具差异更大。

具体排名与数值以论文数据为准，本调研未逐项复现。

### 4.4 文档 AI 与端到端方案

| 工具 | 形态 | 适用场景 |
| --- | --- | --- |
| 云厂商文档智能（腾讯、阿里、华为、百度） | API | 快速接入，按量计费 |
| 合合 TextIn | API 与私有化 | 需要私有化部署 |
| MinerU | 开源 | 文档转结构化，含公式与表格 |
| Docling | 开源 | 文档转 Markdown，适配大模型流程 |
| marker | 开源 | PDF 转 Markdown，速度较快 |

这类工具的共同特点是**面向通用文档**，输出为 Markdown 或通用结构化数据。用于银行流水需再做一轮字段映射与校验，不能直接产出业务字段。

### 4.5 OCR 云服务选型维度

| 维度 | 说明 |
| --- | --- |
| 单次页数上限 | 影响是否可以整份上传 |
| 单文件大小上限 | 影响大流水文件处理 |
| 格式覆盖 | PDF、图片、扫描件的支持程度 |
| 表格结构输出 | 是否返回单元格坐标与合并信息 |
| 能力分层 | 是否区分通用识别与复杂版式 |
| 批量与异步 | 是否有批量接口与回调 |
| 部署方式 | 公有云、私有化、离线 |
| 计费方式 | 按页、按次、套餐包 |

选型时准确率只是其中一项，页数上限与输出结构对工程实现的影响更大。

### 4.6 技术选型结论

| 环节 | 结论 |
| --- | --- |
| 合规性判断 | pypdf 读结构与加密状态 |
| 文本与坐标 | pdfplumber 为主，PyMuPDF 补充渲染 |
| 表格重建 | 自建坐标聚类，规则表格优先 |
| 无模板兜底 | 云 OCR 或通用版面模型 |
| 数值字段 | 不使用生成式模型，避免不可复现 |
| 摘要语义 | 规则与词库为主，语言模型仅作辅助 |
| 版式指纹 | 自建，基于文本与坐标特征 |

## 6 差异化机会

### 6.1 已商品化，不宜重复投入

| 能力 | 原因 |
| --- | --- |
| 通用 OCR 与文字识别 | 云厂商按量计费，价格透明 |
| 表格转 Excel | 工具化程度高 |
| 简单收支分类 | 规则即可实现，无壁垒 |

### 6.2 存在但未做透

| 能力 | 现状 | 可切入点 |
| --- | --- | --- |
| 流水验真 | 多停在三要素，结论笼统 | 分离证据与结论，输出可核查项 |
| 风险指标 | 以固定模板为主 | 口径版本化，指标可回溯到交易 |
| 模板覆盖 | 靠人工积累，无治理流程 | 建立需求池、版本与失效告警 |

### 6.3 空白区
