# 这个部分在业务里承担什么

把一份文件变成一件**有人负责、可追溯、可复核**的事：谁交的、什么时候、走到哪一步、结论是什么、谁看的、谁导出的。

后端不做判断，负责**让判断有出处**。

# 受理环节的业务要求

## 什么样的文件可以进来

五道关，顺序固定，命中即退，且必须告诉对方是哪一关：

| 顺序 | 关卡 | 业务含义 | 退回时怎么说 |
| --- | --- | --- | --- |
| 1 | 是不是 PDF | 不是我们就解析不了 | 换成 PDF |
| 2 | 文件完整吗 | 下载中断的文件看起来和正常的一样 | 重新下载 |
| 3 | 有没有口令 | 加密件我们打不开 | 去掉口令或给口令 |
| 4 | 有没有文字层 | 截图和扫描件没有文字，做不了抽取 | 用官方导出件 |
| 5 | 是不是只有一家银行 | 混装会导致模板错配，结论全错 | 分开上传 |

**第 4 关的性质要说清**：它不是质量判断，是来源判断——没有文字层说明它不是从银行渠道正规导出的。

## 同一份文件重复提交怎么办

必须返回**原来那个任务**，不新建。理由：重复建任务会让同一份材料被核验两次，报告出现两个版本，谁都不知道该以哪份为准。

# 任务环节的业务要求

## 一个任务的状态必须说人话

| 状态 | 对业务的含义 | 用户可理解的说法 |
| --- | --- | --- |
| PENDING | 已收下，还没开始验 | 已收件 |
| CHECKING | 在验入口五项 | 正在检查文件 |
| PARSING | 在抽明细 | 正在读取流水 |
| NEED_SUPPLEMENT | 缺页或缺月，等补 | 材料不完整，需要补 |
| VERIFYING | 在做四层核验 | 正在核对 |
| REPORTING | 在用结论生成报告 | 正在生成结果 |
| DONE | 可以看了 | 已完成 |
| FAILED | 中途出错，可重跑 | 处理失败 |

规则：状态只能往前走，**不能跳级**；任何跳级都是 bug，不是优化。

## 什么时候允许重跑，什么时候允许补件

| 动作 | 允许的前提 | 不允许时的业务理由 |
| --- | --- | --- |
| 重跑 | 已失败 | 跑着的任务重跑会生成两份结果 |
| 补件 | 停在「需要补」 | 不缺件时补件会让明细与文件对不上 |
| 删除 | 未进入核验 | 已出结论的任务删掉就失去了追溯依据（所以只做逻辑删除） |

# 载体分流（先判载体，再走关卡）

材料进来第一件事不是查合规，是**判它是哪一类载体**，因为后面每一步都不一样。

| 判据 | 结论 | 依据 |
| --- | --- | --- |
| 是 PDF 且能提取出文字 | electronic | 有点击可选的文字层 |
| 是 PDF 但提不出文字 | image | 扫描或图片嵌入的 PDF |
| 是 JPG/PNG，且画面有噪点、光照不均、轻微透视 | image | 自然的拍摄或扫描特征 |
| 是 JPG/PNG，且背景纯色、边沿锐利、无噪点、出现状态栏或通知栏 | screenshot | 屏幕截图特征 |

判定在服务端做，**不接受前端自称**：客户端说是电子件不能信，否则绕过结构取证。

## 三类在流程上的差异

| 环节 | electronic | image | screenshot |
| --- | --- | --- | --- |
| 合规五项 | 全查 | 查格式、大小、分辨率、模糊度、是否混装 | 同 image |
| 核对方式 | 结构取证 + 内容 + 账务 | 图像取证 + OCR + 内容 + 账务 | 图像取证 + OCR + 内容 |
| 结论上限 | 未发现异常 | 未发现异常 + 核验受限 | 来源可疑（封顶） |
| 人工复核 | 不需要 | **强制**（报告标待复核） | 强制，且不得作为授信依据 |
| 指标 | 正常出 | 正常出，标注数据来源为 OCR | 出，但仅作参考 |

## 图片要先过三关，不合格直接退回

| 关 | 判据 | 退回理由怎么讲 |
| --- | --- | --- |
| 分辨率 | 短边 ≥ 1000px | 图片太小，关键数字会糊 |
| 清晰度 | 关键区域的文字可辨 | 哪里看不清就指哪里 |
| 完整度 | 页眉页脚、表头、合计行都在画面内 | 缺边会被裁掉整列 |

三关不合格不进入 OCR：**OCR 出来的错数比退回更糟**，因为它看起来是真的。

# 核验环节的业务要求

| # | 要求 | 为什么 |
| --- | --- | --- |
| K1 | 四层核验各自留结论，不合并成一个分数 | 合并会掩盖关键差异，例如文件层通过但账务层算不了 |
| K2 | 每条结论必须挂到具体交易与页码 | 不能指向原页的结论，审批人无法复核 |
| K3 | 只有「存在不一致」可以阻止出报告 | 其余状态都要出报告，并写明核验不完整 |
| K4 | 核验不通过时，要能回答「是抽错了还是材料本身有问题」 | 两者处置完全不同：前者重跑，后者退回 |
| K5 | 模板由银行提供，平台不判断模板能不能正确识别 | 判断模板质量不是我们的职责，也做不到 |

# 报告环节的业务要求

| # | 要求 | 为什么 |
| --- | --- | --- |
| R1 | 只有一份报告 | 给借款人看会引发反向选择 |
| R2 | 只有银行侧三类角色能看 | 报告是给判断者用的，不是给被判断者用的 |
| R3 | 报告版本只增不改 | 改了旧版本，之前导出过的纸面就与系统不一致 |
| R4 | 每次导出留痕：谁、何时、哪一版、导出格式 | 报告离开系统后只能靠这条记录追溯 |
| R5 | 报告里不出现建议与评分 | 判断是银行的事 |
| R6 | 报告必须能回答「为什么是这个结论」 | 一张只有结论的报告等于没有报告 |

# 批量筛查的业务要求

| # | 要求 | 为什么 |
| --- | --- | --- |
| S1 | 批量与单份共用任务概念，用类型区分 | 概念一致才不会被当成两套系统维护 |
| S2 | 命中要给位置与规则编码 | 复核人要能回到那笔去看 |
| S3 | 复核结论要留痕，且不覆盖原始命中 | 原始命中是证据，复核意见是判断，两者不能混 |
| S4 | 平台只给线索，不做冻结、报送 | 处置权在银行 |

# 权限与留痕的业务要求

| # | 要求 | 为什么 |
| --- | --- | --- |
| P1 | 五类角色：借款人、审批人、模板管理员、运营管理员、系统管理员 | 角色不清就无法归因 |
| P2 | 借款人只能看到自己那份任务的状态 | 越权看别人的材料是重大事故 |
| P3 | 所有写操作留痕，审计不可修改 | 出事时要能还原「谁在什么时候做了什么」 |
| P4 | 脱敏在服务端完成 | 前端脱敏等于没脱敏 |

# 与数据组的读写协商

## 谁写哪张表

| 表 | 后端写 | 数据组 | 说明 |
| threshold（阈值） | 存与版本化 | 建表 | **阈值内容由算法组定义**，后端不自行设定默认值 |
| --- | --- | --- | --- |
| staff_user | 建与改（业务操作） | 建表、索引 | 停用不删 |
| file_obj / task / bank_account / txn | 写 | 建表、分区、索引 | 后端只按契约字段写 |
| metric_value / report | 写（只增） | 建表、只读视图 | 历史不改 |
| template / rule | 写新版本 | 建表、唯一索引 | 只增不改 |
| audit_log | 只插入 | 独立库、备份 | 后端无更新删除权限 |

结构（列、索引、分区）归数据组；数据归后端。**后端不执行任何 DDL**，启动只做「缺表则建」兜底。

## 事务与批量

| 场景 | 做法 | 为什么 |
| --- | --- | --- |
| 建任务 | 文件记录 + 任务同事务 | 不能有任务没文件 |
| 写明细 | 单任务全部明细同事务 | 半份明细会被当成完整材料 |
| 写报告 | 报告 + 指标同事务 | 报告不能指向不存在的指标 |
| 跨库（报告库、审计库） | 分两次提交，失败记补偿标记 | 三库独立部署，无法跨库事务 |
| 批量写入 | 每批 500 行，失败重试 2 次后整任务失败 | 大事务会锁表 |

## 结构与字段变更的规矩

1. 先改 `contract.md`，再改迁移，再改代码，最后发版。
2. 新增字段必须可空或带默认值，**不许删旧字段**（前端与算法可能还在用）。
3. 结构变更只能在维护窗口执行，运行时禁止改表。
4. 每日对账：任务数、明细数、报告数三者能对上；对不上报警。

# 并发与竞态

| 场景 | 风险 | 处理 |
| --- | --- | --- |
| 同一文件重复提交 | 生成两个任务 | 哈希判重 + 唯一索引，冲突时返回已有任务 |
| 队列重复投递 | 同一阶段跑两遍，明细翻倍 | 消息带阶段号，同任务同阶段只执行一次 |
| 两人同时重跑 | 两份结果互相覆盖 | 状态机 + 版本号乐观锁，后到者被拒 |
| 补件与解析同时发生 | 明细与文件对不上 | 补件期间任务锁在「待补件」，解析不可入 |
| 导出并发 | 打爆内存 | 异步作业，单账号同时最多 3 个 |
| 同一模板并发解析 | 重复加载 | 模板缓存，按版本失效 |

读写分离：报表与看板走只读账号与视图，避免长查询拖慢写入。

连接池：上限固定、获取超时、慢查询阈值 500ms 记日志；连接泄露视为缺陷。

# 安全验证

| 面 | 要什么 | 不要什么 |
| --- | --- | --- |
| 认证 | 令牌有效、过期即拒、后台与前台令牌互不通用 | 用 URL 传令牌 |
| 授权 | 角色到接口的矩阵；对象级校验（借款人只能看自己的任务） | 只在前端隐藏按钮 |
| 越权 | 水平越权（他人任务）与垂直越权（低角色调高接口）都要拦 | 返回空列表冒充成功 |
| 上传 | 大小限制、真实类型校验（看文件头不看扩展名）、文件名清理、压缩炸弹防护、行内病毒扫描 | 直接按扩展名放行 |
| 注入 | 参数化查询 | 拼接 SQL |
| 重放 | 幂等键 + 时间戳窗口 | 无限制重复提交 |
| 脱敏 | 出口统一脱敏 | 日志里记明文卡号 |
| 审计 | 写操作全留痕，审计不可改 | 记录可编辑 |

## 越权的两种典型表现

| 类型 | 例子 | 正确返回 |
| --- | --- | --- |
| 水平 | 借款人 A 请求借款人 B 的任务号 | 403 E_FORBID，不返回 404 也不返回空 |
| 垂直 | 审批人调用系统管理接口 | 403 E_FORBID |

返回 404 会让对方以为任务不存在；返回空列表会让他以为没数据。两者都掩盖了越权事实。

# 与前端的调用约定（React）

| 项 | 约定 | 为什么 |
| --- | --- | --- |
| 协议 | REST + JSON，HTTPS | 简单、可缓存控制、易排查 |
| 开发期转发 | Vite 代理 `/api` 到 8000 | 避开跨域，生产由 Nginx 同源 |
| 认证 | `Authorization: Bearer <token>`，前台 bs_token、后台 bs_admin_token | 两套身份不混用 |
| 响应 | `{code, message, data}`；HTTP 状态与业务码同时用 | 便于通用拦截器处理 |
| 分页 | `page`（从 1）与 `size`，返回 `total` | 前端算不出总数 |
| 上传 | multipart/form-data，前端用 onUploadProgress 显示进度 | 大文件要进度 |
| 轮询 | 间隔 2 秒，终态即停；状态接口只返回必要字段 | 轮询不是全量拉详情 |
| 长任务 | 导出走 job：先拿 job_id 再轮询下载地址 | 同步导出会超时 |
| 取消 | 页面卸载用 AbortController 取消在途请求 | 避免卸载后 setState |
| 金额与时间 | 金额字符串、时间带偏移字符串 | 浮点丢精度、时区错位 |
| 错误文案 | 后端给 code，前端按受众选文案 | 同一错误两种说法 |
| 缓存 | 业务接口 `no-store` | 材料与结论不可被中间层缓存 |
| 兼容 | 新增字段向前兼容，不删旧字段 | 前后端发版不同步 |

## 前端最常踩的三个坑（后端要主动避免）

| 坑 | 后端怎么做 |
| --- | --- |
| 金额被当数字运算 | 金额一律字符串返回，文档写明不许运算 |
| 时间为空导致显示 1970 | 空值返回 null，不返回 0 或空串 |
| 状态枚举前端猜 | 每个状态返回一句中文含义字段 status_text |

# 验收口径（业务判断）

| # | 怎么算做对了 |
| --- | --- |
| V1 | 拿一份合规件和五份不合规件，五类都退回且原因正确 |
| V2 | 同一份文件交两次，只产生一个任务 |
| V3 | 给一个失败任务，运营能自己重跑成功，不需要找人 |
| V4 | 任一结论都能在 30 秒内点到原页 |
| V5 | 借款人账号直接请求报告接口，被拒绝 |
| V6 | 导出十次，审计里能看到十条记录 |
| V7 | 任务状态从创建到完成，没有任何跳级 |

# 与其他部分的交界

| 交界 | 我方要什么 | 我方给什么 |
| --- | --- | --- |
| 算法 | 四个能力：解析、四层核验、指标、命中；结论要可回溯 | 明细、利率表、规则集 |
