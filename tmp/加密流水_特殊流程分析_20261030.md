**关键判断：这不是「一份加密 PDF」，而是「一个加密压缩包，里面装一份 PDF」。**
两者业务处置完全不同：前者系统能识别格式并要求口令；后者连格式都不在受理范围内。

# 二、它暴露的四个业务问题

| # | 问题 | 客户视角 | 银行视角 |
| --- | --- | --- | --- |
| 1 | 压缩包不在受理格式里 | 「我下载的就是这个文件」 | 不代解，客户要自己解压，多数人不会 |
| 2 | 口令从哪来、谁有权问 | 「密码是身份证后六位吗？」 | 系统自动要口令，等于代客保管密码 |
| 3 | 口令错了怎么办 | 反复试、反复失败 | 要有次数上限与转人工规则 |
| 4 | 双层口令 | 「里面 PDF 可能还要密码」 | 一次材料问两次密码，流程要接住 |

# 三、全链路：这份材料会卡在哪

| 环节 | 正常流程 | 这份材料 | 结论 |
| --- | --- | --- | --- |
| 收件 | 上传后回执 | 上传的是 zip | **卡第 1 步**：格式不受理 |
| 过门槛 | 判格式/加密/清晰度/混装 | 得先解包才能判 PDF | 顺序反了：先解包再过关 |
| 解包 | 「打开压缩包」 | 要口令，最多 3 次 | 新增一个业务步骤 |
| 载体判定 | 电子件/影像件/截图 | 解出 PDF 后才判 | 判定推迟，客户等待变长 |
| 版式识别 | 命中银行模板 | **招行版式**，不是工行 | 没有招行模板就走通用兜底 |
| 读内容 | 电子件直抽 / 影像件 OCR | PDF 是否带文字层，解开才知道 | 现在**无法判断** |
| 验真假 | 四层 | 电子件走 11 项结构取证 | 解包后才能做 |
| 算指标 | 40 项 | 依赖明细 | 同上 |
| 出报告 | 银行侧一份 | 报告要写「依据：系统代解 1 份」 | 材料清单需标明代解 |

**结论：比普通 PDF 多两步——解包、要口令，且都发生在「过门槛」之前。**

# 四、口令环节的业务规则（本轮已按此实现）

| 规则 | 做法 | 理由 |
| --- | --- | --- |
| 谁问 | 收件时由系统问客户，银行员工不代问 | 避免员工接触客户密码 |
| 问几次 | **最多 3 次**，第 3 次错就停 | 防暴力试探，也防无限重试 |
| 问不到 | 转补件：请客户自行解压后上传 PDF | 最安全也最快 |
| 存不存 | **不存库、不进日志、只在内存用一次** | 口令是敏感凭据，存了就是负债 |
| 留痕 | 留「试了几次、成功还是放弃」，不留口令本体 | 审计要能回答「谁在何时试过几次」 |

# 五、银行与版式：这次会踩的坑

1. **银行对不上**：文件名是招行，你说的是工行；模板按「银行名 + 表头」命中，**没有招行模板就会走通用兜底**，列可能错位。
2. **需要先标一份招行模板**：用解包后的 PDF 在标注页标一次并导出，才能稳定解析。
3. **样例是客户真实件**：不得入库；已把 `*.zip` 与根目录 `*.pdf` 加进忽略清单，该文件不会被提交。

# 六、系统现在能做什么、不能做什么

| 能力 | 现状 |
| --- | --- |

| 口令输入框 | **能**：选择该 zip 后弹出，提示常见口令位置 |
| 口令错误提示与次数 | **能**：「还可以试 N 次」，3 次后停止并建议补件 |
