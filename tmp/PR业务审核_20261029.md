骨架阶段不实现是正常的。但发现了四个**会一路带下去**的问题。

## B-01（P1）页面上泄漏了判定口径，还顺手教了怎么绕

证据：`frontend/src/pages/UploadPage.tsx` 材料说明段——

> 「截图：可以选择，但来源难以核验，可能无法作为授信依据。」

业务后果：

1. 借款人看到「截图不行」，最自然的反应是**打印出来再拍照**，正好落进影像件路径（B 类），而影像件本来是降级核验、需人工复核的。我们等于把绕过路线写在了门上。
2. 这与「不给借款人看结论」是同一个风险的两个面：不给结论，却给了判定规则。

建议：借款人侧只说「建议使用手机银行导出的 PDF，处理最快」，**不解释截图为什么不行**。判定规则留在银行侧文档与报告里。

## B-02（P0）清晰度与完整度两关没有归属

design 要求图片过三关：分辨率、清晰度、完整度。

- 前端只做了分辨率（`shortSide < 1000`）；
- 后端的 tasks 里没有清晰度/完整度任务；
- 算法 tasks 里也没有。

结果：**两侧都不做**。上传一张糊到看不清金额的图，系统会一路走到 OCR，抽出一堆低置信数字，再判「识别不可靠，转人工」。这本该在门口拦掉。

## B-03（P1）加密件没有出口

契约有 `E_ENCRYPT`、有双受众文案，但：

- 前端没有口令输入（FE-07 未拆）；
- 后端没有实现该分支。

用户拿到加密流水，只会反复上传、反复失败。

## B-04（P1）后端没有文件头校验，前端 MIME 可绕过

前端判定用 `candidate.type` 与扩展名；后端一行校验都没有。改个扩展名（或构造请求）就能把任意文件送进解析。业务上「20MB、PDF/JPG/PNG」这条线目前只存在于浏览器里，**不是防线**。

## B-05（P1）架构上还没分两个应用

业务要求：借款人 5173、银行 5174，两套 Token 互不读取，**报告只给银行**。

现状：单个 `frontend/`，单个 vite 端口 5173，vite 代理已就绪但无路由、无守卫、无 Token。

风险不是「现在错了」，而是**将来加银行侧页面时最省事的做法就是往同一个应用里加**——一旦如此，借款人侧的 bundle 里就带着报告页的代码与接口路径，「报告只给银行」只能靠后端拦，前端防线形同虚设。

建议：在开始 B1 之前就把两个应用拆开，越晚拆越贵。

## B-06（P0）借款人没有身份

页面无登录、无实名、无手机验证；契约的 `task` 表也**没有 `submitted_by` 之类的字段**。

直接后果有两个，见第三节。

# 三、幂等性

## I-01（P0）幂等键会导致跨用户拿到别人的任务

契约第 12 行：

> 幂等 | 创建任务以文件哈希判重，重复提交返回原 task_id

契约第 119 行 `task` 字段：`id、biz_no、task_type、channel、file_id、carrier、template_id、template_version、status、check_result、period_start、period_end、hits`——**没有提交人**。

业务后果：

| 场景 | 现状会发生什么 |
| --- | --- |
| 同一借款人重复上传 | 返回原任务 ✔ 正确 |
| 中介给五个客户用了同一份包装流水 | 后四人拿到**第一个人的 task_id**，看到别人的任务状态；将来若开放报告接口，就是跨用户数据泄露 |
| 审计 | 一份文件只记一个提交人，其余四人的提交行为无痕迹 |

中介批量包装流水是本项目最现实的欺诈场景之一，这不是理论风险。

修正（必须改契约，仅 PM/PD 可动）：幂等键改为 `(submitter_id, file_sha256)`；语义拆成两条——

- 同人同文件：返回原任务，并提示「该材料已提交过」；
- 不同人同文件：新建任务，同时标记「同一文件被多人提交」，这本身是强风险信号，应进报告。

## I-02（P1）重复提交且原任务已完成时，交互未定义

若返回原任务，前端跳进旧任务，用户会以为「我新传的没生效」。需产品定一句文案。

## I-03（P2）前端无防连点

当前按钮恒 disabled 所以不暴露；接入上传时必须 `loading + disabled`，否则双击就是两次请求（即使后端幂等，也会产生两条审计）。

| 进程模型 | uvicorn 单进程单 worker | 开发够用；100 QPS 目标未验证 |

# 五、异常处理

## 后端（P0）：错误结构不符合契约

`backend/main.py` 无全局异常处理器、无统一响应包装、无错误码。现在任何错误都是 FastAPI 默认结构（`{"detail": ...}`），而契约要求 `{code, message, data}`。

后果：前端接入时要么解析失败，要么为 4xx/5xx 写一套特殊分支，等于 FE-03 要走两遍。

**建议调整顺序：BE-03（统一响应与错误码）应与 BE-05（上传接口）同批，不要等接口写完再补。**

同时缺：

| 缺什么 | 影响 |
| --- | --- |
| request-id / trace id | 出问题无法从用户截图定位到日志 |
| `/health` | 用 `/docs` 当探活，Swagger 一关就误判服务挂了 |
| 日志脱敏策略 | 将来请求体里会有卡号，现在没有任何约束 |
| 422 参数错误的统一包装 | 校验失败返回框架默认格式 |

## 前端（P1）：错误被压成一句话

`catch` 里一律转成中文文案，无错误码。接入后端后必须重写为「码 → 文案」映射，否则两套受众文案（借款人重传导向 / 审批人核对导向）没法实现。

做得对：`role="alert"`、`aria-live="polite"`，读屏可用。
