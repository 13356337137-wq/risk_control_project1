# 这个部分在业务里承担什么

让每一份材料的处理过程**事后能还原**：谁交的、什么时候、谁看的、改过什么、现在还在不在。

数据是这套系统里唯一不能被「重跑一次」修复的东西——跑错了可以再跑，数据丢了就是丢了。

# 三条业务底线

| # | 底线 | 为什么 |
| --- | --- | --- |
| D1 | 结论与证据只增不改 | 已经导出给客户的报告，系统里必须能对上 |
| D2 | 审计记录只追加，不可改不可删 | 出事时要能还原真实过程，可改的记录等于没有记录 |
| D3 | 敏感字段不落明文 | 卡号与证件号一旦进库，泄漏风险就跟着整个生命周期 |

# 数据要回答的业务问题

| 谁问 | 问什么 | 靠什么回答 |
| --- | --- | --- |
| 审批人 | 这份材料的结论是怎么来的 | 报告、指标、证据坐标三者对得上 |
| 运营 | 今天进了多少件、失败多少、卡在哪一步 | 任务状态与时间的分布 |
| 合规 | 谁看过、谁导出过、谁改过 | 审计记录 |
| 客户 | 我的材料还在不在、能不能删 | 留存策略与逻辑删除 |
| 开发 | 这个字段是什么意思、能不能改 | 数据字典 |

# 三类载体的存储差别

| 内容 | 电子件 | 影像件 | 截图 |
| --- | --- | --- | --- |
| 原件 | 存 | 存 | 存 |
| 宽高与页数 | 页数 | 宽高 + 页数 | 宽高 |
| OCR 中间结果 | 不需要 | **必须存**（每行的坐标与置信度） | 必须存 |
| 载体判定 | 记在 file_obj 与 task | 同 | 同 |

**为什么 OCR 中间结果必须存**：人工复核时要能回到「这个数字是被识别成这样的」，只存最终明细等于把识别过程丢了，出了争议无法复现。

## 影像件的业务约束

| # | 规则 | 理由 |
| --- | --- | --- |
| R7 | 原件与 OCR 中间结果同时保留，留存期与明细一致 | 复核与追溯都要用 |
| R8 | OCR 中间结果只增不改 | 改了就无法还原当时的识别状态 |
| R9 | 载体类型存两份（文件与任务） | 统计按任务查，回溯按文件查，两边都要快 |
| R10 | 图片原件不压缩存储 | 压缩会破坏取证痕迹，也影响复核判断 |

# 数据怎么分

| 库 | 装什么 | 业务理由 |
| --- | --- | --- |
| 业务库 | 人、文件、任务、账户、明细、模板、规则 | 这些随任务生命周期走，查得最频繁 |
| 指标与报告库 | 指标、报告 | 一次写、多次读，且要长期保留 |
| 审计库 | 审计记录 | 单独存放、单独备份，才能证明没被改过 |

**为什么明细与报告要分开**：明细是证据，报告是结论。证据量大力求快，结论量小求稳；放一起会互相拖累。

# 关键业务规则

| # | 规则 | 为什么 |
| --- | --- | --- |
| R1 | 交易明细保留页码与坐标 | 没有位置，证据就无法回到原页 |
| R2 | 被剔除的明细不删除，只标注原因 | 审批人问「为什么这笔不算收入」，要能指出来 |
| R3 | 指标名与值同一行存放 | 分开存会出现「有值没名」的脏数据 |
| R4 | 报告与模板、规则都只增不改，靠版本号区分 | 改旧版会让历史报告无法复现 |
| R5 | 任务删除只做逻辑删除 | 物理删除会留下孤儿明细，审计也对不上 |
| R6 | 跨库不建外键，用任务号关联 | 三库独立部署与独立备份，外键会把它们绑死 |

# 脱敏的业务口径

| 字段 | 谁能看到原文 | 对外显示 |
| --- | --- | --- |
| 银行账号 | 无人（系统内不提供查看原文的入口） | 前四后四 |
| 姓名 | 审批人在授权范围内 | 留首字 |
| 身份证号 | 无人 | 只存哈希，不提供反查 |
| 手机号 | 无人 | 中间四位掩码 |
| 交易对手方 | 审批人 | 按角色脱敏 |

原则：**默认不可见，按角色开口子**；不是默认可见再打码。

# 留存与销毁

| 数据 | 留存 | 到期怎么处理 |
| --- | --- | --- |
| 交易明细 | 三年 | 归档到冷存储，不直接删 |
| 报告 | 三年 | 同上；已导出的纸质件不受系统控制 |
| 审计 | 不设期限 | 永久保留 |
| 原始文件 | 三年 | 与明细同期 |

客户要求删除时：删明细与文件，保留报告摘要与审计记录（履行合规义务所必需）。

# 权限的业务要求

| 账号 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 读写账号 | 业务库与报告库读写 | 不能改审计 |
| 只读账号 | 只能读脱敏视图 | 不能写任何表 |
| 审计写账号 | 只能插入审计 | 不能读业务数据 |

为什么分成三个：**能改业务数据的人不能改审计**，否则出事后无人能证明清白。

# 验收口径（业务判断）

| # | 怎么算做对了 |
| --- | --- |
| V1 | 抽一份已完成任务，明细笔数、指标值、报告结论三者一致 |
| V2 | 删掉一个任务，系统里仍能查到它曾经存在（逻辑删除 + 审计） |
| V3 | 拿只读账号试着改一条明细，被拒绝 |
| V4 | 从备份恢复到临时库，行数与校验和与生产一致 |
| V5 | 用借款人视角查任何接口，拿不到明文卡号与身份证 |
| V6 | 给一个陌生人看数据字典，他能说出每个字段是什么 |

# 与其他部分的交界

| 交界 | 我方要什么 | 我方给什么 |
| --- | --- | --- |
| 后端 | 只按契约读写、不自行加字段 | 表结构、索引、迁移、脱敏视图 |
| 算法 | 指标口径版本 | 利率表与计息规则表 |
| 前端 | 不接触数据库 | 脱敏后的数据由后端提供 |

# 不做

| 不做 | 谁做 |
| --- | --- |
| 业务判断与状态流转 | 后端 |
| 指标计算 | 算法 |
| 页面呈现 | 前端 |
| 数据对外提供 | 银行（我们不做导出以外的外发） |
